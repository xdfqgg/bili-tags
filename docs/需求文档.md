# 需求文档（PRD）— bili-tags

> 日期：2026-08-22 ｜ 状态：✅ 已评审通过（Step 0 产物）
> 来源：brainstorming 流程，与用户逐条确认后定稿

## 1. 背景与问题

用户刷 B 站时容易被推荐算法带偏（大数据推流导致时间流失）。希望夺回信息流的控制权：让扩展把自己选择的视频（按标签关键词搜索而来）随机混入 B 站推荐流，使浏览池中始终混有主动选择的内容。

## 2. 用户故事

> 作为 B 站用户，我想要扩展把我按标签关键词选好的视频卡片随机混入推荐流，以便我刷到的池子里始终混有自己主动选的内容，而不是 100% 被算法供给。

## 3. 范围（MVP）

| 项 | 决策 |
|----|------|
| 平台 | Chrome 扩展，Manifest V3 |
| 生效页面 | 仅 `www.bilibili.com` 推荐页首页（无限流） |
| 核心功能 | ① options 页配置标签（标签名 + 搜索关键词 + 颜色）② background 调 B 站 API 按关键词搜索并缓存 ③ content script 以概率 P 随机混入视频卡片 ④ 注入卡片带标签 badge |
| 混入节奏 | 随机掺入，默认 P = 30%，可在 options 页配置 |
| 数据存储 | `chrome.storage.local`，仅本地 |

## 4. 明确砍掉的需求（与用户确认）

- ❌ 顶部「我的视频卡片」面板 —— AI 生成需求，对核心价值（混入推流）无贡献
- ❌ `parseVideoId` 解析页面卡片 BV 号 —— 需求从「标记已有卡片」变为「注入新卡片」后无用
- ❌ 多页面生效范围 —— MVP 只做推荐页首页
- ❌ 三档实现等级 / JSON 输出格式等原模板流程约束 —— 在 Claude Code 环境无意义

## 5. 架构（四组件）

```
┌─────────────┐  配置读写   ┌──────────────────┐
│  options 页  │ ◄────────► │ chrome.storage    │
│ (标签/概率)  │            │    .local         │
└─────────────┘            └────────┬─────────┘
                                    │ 读配置
┌─────────────┐  消息通信   ┌───────▼─────────┐   B站API  ┌─────────┐
│ background  │ ◄─────────► │  content script  │ ────────► │ B站搜索  │
│ (API请求层) │             │ (注入逻辑)       │  结果缓存  │ 接口     │
└─────────────┘             └─────────────────┘ ◄───────── └─────────┘
```

- API 请求放 background：content script 受页面 CORS 限制，background 持 `host_permissions` 可合法跨域
- 注入逻辑放 content script：只有它能操作页面 DOM

## 6. 数据流（一次注入的发生过程）

1. 用户在 options 页配置标签：`{name: "学习", keyword: "前端教程", color: "#00AEEC"}`，P = 30%
2. background 定时（缓存 TTL 30 分钟）调 B 站搜索 API，每个关键词缓存 Top 20 条结果（BV号 / 标题 / 封面 / 时长 / UP主）
3. content script 用 MutationObserver 检测推荐流新增卡片
4. 以 P 概率决定是否注入；注入则从缓存池随机取一条（同一页面会话内不重复），按 B 站卡片结构克隆卡片（封面 + 标题 + 时长 + UP主 + 标签 badge），点击跳转视频
5. badge 显示标签名与标签色，一眼识别「这张是我掺的」

## 7. 数据模型（storage schema）

```json
{
  "enabled": true,
  "probability": 0.3,
  "tags": [{ "name": "学习", "keyword": "前端教程", "color": "#00AEEC" }],
  "cache": {
    "前端教程": { "fetchedAt": 1692000000000, "videos": [ { "bvid": "...", "title": "...", "pic": "...", "duration": "...", "author": "..." } ] }
  }
}
```

## 8. 错误处理与降级（三层防御）

| 故障 | 表现 |
|------|------|
| B 站 API 失败 / 接口变更 | 不注入任何卡片；options 页显示「获取失败」状态；页面本身不受影响 |
| DOM 结构变更（B 站改版） | 找不到锚点 → 停止注入 + 控制台警告；绝不向页面抛异常 |
| 用户未配置任何标签 | 扩展静默待机，不注入 |

## 9. 测试策略

- **Jest 单测**：概率判断、缓存池随机取 + 会话内去重、关键词配置校验、badge DOM 构造
- **Puppeteer E2E**：本地 mock HTML 卡片流（不爬真实 B 站页面），断言注入卡片 + badge 出现

## 10. 验收标准（Acceptance Criteria）

1. Chrome 加载 unpacked 扩展无报错
2. 推荐页首页配置标签后，滚动刷新时概率性出现带标签 badge 的注入卡片，点击跳转对应视频
3. options 页关闭开关后不再注入
4. API 失败时：页面不崩、不注入、options 显示错误状态
5. 数据仅存本地；除 B 站 API 外无任何外部网络请求
6. 同一页面会话内注入的视频不重复

## 11. 合规底线

- 不采集用户浏览数据、不上传任何信息、无自有服务器
- API 只读、缓存限频、不伪造请求头

## 12. 遗留问题（Step 3 侦察确认）

- B 站搜索 API 具体端点、是否需要 wbi 签名
- 推荐页卡片真实 DOM 结构与注入锚点
- `host_permissions` 精确域名清单
